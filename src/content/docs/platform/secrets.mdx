**Using Warp Factories?** Follow [Managing factory secrets](https://docs.warp.dev/factories/secrets/) to create secrets and grant agents access in the current web app. The instructions on this page cover supported legacy workflows, including the {VARS.WARP_AGENT_CLI}.

Use the [{VARS.WARP_AGENT_CLI}](/agents/cli/oz-cli/) to create, list, rotate, and delete managed secrets for standalone cloud-agent workflows. The commands remain supported.

## Secret scopes

Secret ownership determines which credentials a run is eligible to use; its configuration determines which eligible secrets are injected.

### Team secrets

Team secrets belong to the team. Use narrowly scoped service-account credentials rather than credentials tied to an individual person. Attach secrets by name to a [cloud agent](/platform/agents/) or its execution configuration.

### Personal secrets

Personal secrets belong to your user account. Runs without your user context cannot use them. They aren't listed in the factory secret picker; use team secrets for factories.

## Managing agent secrets with the CLI

In the {VARS.WARP_AGENT_CLI}, use the `oz secret` commands. Log in first as described in the [CLI quickstart](/agents/cli/oz-cli/quickstart/).

### Creating a secret

Create a team secret interactively:

```bash
oz secret create --team METABASE_API_KEY
```

The CLI prompts for the credential without displaying it. For a personal secret, replace `--team` with `--personal`.

To read a credential from a file, replace `SECRET_FILE` below with its path. Protect the file and exclude it from version control.

```bash
oz secret create --personal --value-file SECRET_FILE METABASE_API_KEY
```

### Adding descriptions

Use a description to record ownership and rotation requirements without including the credential:

```bash
oz secret create --team \
  --description "Rotate every 2 weeks; owned by platform team" \
  METABASE_API_KEY
```

### Updating a secret

Replace the value while keeping the same name and scope:

```bash
oz secret update --team --value METABASE_API_KEY
```

The CLI prompts for the replacement credential. To read it from a file instead, replace `NEW_SECRET_FILE` with the file's path:

```bash
oz secret update --team --value-file NEW_SECRET_FILE METABASE_API_KEY
```

Update only the description:

```bash
oz secret update --team \
  --description "Owned by platform team; rotated monthly" \
  METABASE_API_KEY
```

### Listing secrets

List metadata for secrets you can access:

```bash
oz secret list
```

Stored values aren't displayed.

### Deleting a secret

Delete a team secret:

```bash
oz secret delete --team METABASE_API_KEY
```

The CLI asks for confirmation. Add `--force` to skip confirmation, or replace `--team` with `--personal` for a personal secret.

:::caution
Deletion is permanent and affects workflows that reference the secret. Remove or replace those references first, and revoke the credential in the external service if it must no longer be usable.
:::

### How secrets are made available to cloud agents

Raw-value secrets are injected as environment variables using the secret name. Avoid printing credentials in commands or agent outputs; [secret redaction](/support-and-community/privacy-and-security/secret-redaction/) is a backstop, not a replacement for restricted access.

#### Secret size limit

See the shared [secret size limit](https://docs.warp.dev/factories/secrets/#a-secret-value-is-too-large) and guidance for large payloads.

## Secret availability by trigger type

Runs associated with your user can resolve eligible personal secrets as well as team secrets. Runs without a user context, such as unattended automations, cannot use personal secrets. Ownership alone doesn't attach a secret to a run; check its configured secret list rather than assuming every team secret is injected.

## Scoping secrets to environments and runs

An [environment](/platform/environments/) or [cloud agent account](/platform/agents/) can supply secret references. Run configuration can override the inherited list. Use an explicit list to select the execution secrets needed for a task.

### Environment-level scoping

Attach the credentials an environment needs through its secret configuration. References use names, not stored values, so rotating a secret doesn't require changing its references.

### Run-level scoping

A run's explicit `secrets` list selects its execution secrets. An empty list selects no generic execution secrets; harness authentication and credentials required by attached MCP servers are handled separately. See the [{VARS.WARP_PLATFORM_API} reference](https://docs.warp.dev/factories/api-and-sdk/) for the request shape.
