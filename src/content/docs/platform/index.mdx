<span id="what-is-a-cloud-agent-run" />

Cloud agents execute a request away from your laptop, on Warp-hosted compute or your own infrastructure. For example, an agent can investigate a failed build, review a pull request, or respond to an issue filed in your tracker.

## Start with Warp Factories

For a standing team workflow, start with the [Warp Factories quickstart](/factories/quickstart/). A factory brings together [agents](/factories/factory-agents/), [automations](/factories/automations/), and [evaluation](/factories/measure-and-improve/).

See [how Warp Factories work](/factories/how-factories-work/) for the task lifecycle and human review points.

## Continue a standalone workflow

To start a cloud agent directly from Warp, use the [cloud agents quickstart](/platform/quickstart/). Existing standalone runs, schedules, and integrations have their own configuration and management paths.

Already using the {VARS.WEB_APP}, {VARS.WARP_AGENT_CLI}, or SDKs? See [transitioning from Oz to Warp Factories](/platform/transitioning-from-oz/) before changing an existing workflow.

<span id="observability-and-steerability" />

## Monitor, inspect, and share cloud agent runs

For factory work, open the factory's [Runs page](/factories/factory-dashboard/#inspect-runs). For standalone workflows, use the [Agent Management Panel](/platform/managing-cloud-agents/) in Warp or the [{VARS.WEB_APP} Runs page](/platform/oz-web-app/#runs).

Run records show the task's status, conversation, and outputs so you can check what the agent actually did. Share a session with authorized teammates or send follow-up instructions when the workflow supports continuation.

See [viewing cloud agent runs](/platform/viewing-cloud-agent-runs/) to inspect a transcript, share a session, or continue a standalone run.

## What cloud agents are designed for

* **Event-driven tasks** - Investigate an issue, review a pull request, or examine failed-build logs when an integration or API request starts work.
* **Parallel work** - Divide a larger task into bounded changes, give agents separate working copies, and coordinate their results for review.
* **Recurring maintenance** - Check dependencies, generate tests, or propose documentation updates on a schedule.

Use [factory automations](/factories/automations/) for event-driven work and recurring maintenance in a factory. Standalone workflows have separate [integrations](/platform/integrations/) and [schedules](/platform/triggers/scheduled-agents/). [Multi-agent orchestration](/platform/orchestration/) explains how parent and child agents divide work.

## How cloud agents work

A trigger supplies the request and its context, such as an issue description or pull request diff. The agent works on its configured host with the repositories, tools, and credentials available to it, then produces results such as a branch, pull request, report, or transcript. Define the task's scope and validation commands before starting; a completed run alone doesn't prove the result is correct.

The [{VARS.WARP_AUTOMATION_PLATFORM} overview](/platform/overview/) explains the shared execution model in more detail. For factory hosting choices, see [deployment patterns](/factories/deployment-patterns/). For standalone CLI execution in your own CI or development environment, see [unmanaged execution](/platform/unmanaged-execution/).

## Configure the runtime and tools

A harness runs the coding agent and determines its runtime-specific configuration. An environment groups repositories, a container image, and setup commands; factories manage their workspace by default, with an existing environment available as an option. MCP servers connect the agent to external tools and data.

The shared references cover factory and standalone setup:

* [Cloud agent harnesses](/factories/harnesses/) - Choose a runtime and configure its authentication
* [Environments for factory agents](/factories/environments/) - Reuse an environment when the run needs one
* [MCP servers for agents](/factories/mcp/) - Connect agents to external tools

### Codebase Context

Codebase Context provides indexed repository search to help an agent locate relevant code. Its scope depends on indexing settings and the run's harness. See [Codebase Context in cloud agent runs](/agents/capabilities/codebase-context/#codebase-context-in-cloud-agent-runs) for requirements and availability.

### Centralized configuration

Reusable configuration keeps instructions, tools, and access settings with the workflow instead of repeating them in each request. For factory-wide and per-agent settings, use [definitions as code](/factories/factory-as-code/) and [factory secrets](/factories/secrets/). Standalone resources have their own scopes; the [legacy secrets reference](/platform/secrets/) retains CLI and personal-secret workflows.

<span id="api-access-to-tasks" />

### API access to runs

The API lets scripts, CI jobs, and internal services submit work and inspect its results without the desktop app. Use [factory endpoints](/factories/factory-api/) to send work to a factory. Use [agent and run endpoints](/factories/api-and-sdk/) for standalone runs and to inspect run status, transcripts, and results.

## Using cloud agents with or without the Warp app

For standalone runs outside the Warp app, use the [{VARS.WARP_AGENT_CLI}](/agents/cli/oz-cli/), [{VARS.WEB_APP}](/platform/oz-web-app/), or [API and SDKs](/factories/api-and-sdk/). [Session sharing](/agents/local-agents/session-sharing/) and the [Agent Management Panel](/platform/managing-cloud-agents/) provide inspection paths in Warp.

Use [Handoff](/platform/handoff/) to continue work between local and cloud sessions.
