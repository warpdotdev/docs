import { VARS } from '@data/vars';

Use an existing CI system, Kubernetes controller, or internal scheduler to allocate compute while the {VARS.WARP_AUTOMATION_PLATFORM} routes and tracks each run. Choose one-shot Direct when your scheduler starts a worker for each job. Choose the Command backend when a connected worker should hand tasks to an existing runtime.

## Choosing a pattern

| Pattern | External orchestrator responsibility | Worker behavior | Use when |
| --- | --- | --- | --- |
| One-shot Direct | Allocates a host, starts a worker, and creates a run for its unique worker ID | Runs one accepted task on the allocated host, then exits | Your scheduler creates a VM, pod, or CI runner for each job |
| Command backend | Provides a command or API that accepts a task and owns its compute lifecycle | Stays connected and invokes the dispatch command for each task | Your runtime already exposes a job API, queue, or scheduler |

Both patterns use the managed architecture: Warp accepts triggers and routes runs, while your orchestrator owns compute allocation. If your system should also create and start each agent process without Warp routing, use [unmanaged execution](/platform/self-hosting/unmanaged/).

## Prerequisites

Complete the shared [managed prerequisites](/platform/self-hosting/#managed-prerequisites). The one-shot example below uses one Default Service Account agent key for both the worker and `run-cloud`. When those actions run in different processes, use a self-hosted worker key for the worker and an agent key for the run creator.

Install `oz-agent-worker` from a [published release](https://github.com/warpdotdev/oz-agent-worker/releases). One-shot Direct also requires the {VARS.WARP_AGENT_CLI} on the allocated host. The Command backend worker requires the tools used by your dispatch and cancellation commands.

## Using one-shot Direct

Start a Direct worker with `--one-shot` when your scheduler allocates one host per job. One-shot mode accepts one task, forces `max_concurrent_tasks` to `1`, and exits after that task succeeds, fails, or is cancelled. If no task arrives, the worker stays connected until your orchestrator stops it.

Use a unique worker ID for every job so another worker cannot claim the run.

### Configure the completion timeout

The agent process normally remains available for follow-up prompts for 45 minutes after a conversation completes. Timeout settings use this precedence:

1. A non-negative task-level `config.idle_timeout_minutes` value.
2. The worker's `idle_on_complete` setting or `--idle-on-complete` flag when the task-level value is unset.
3. The 45-minute default when neither value is set.

For a job that must exit immediately, set task-level `config.idle_timeout_minutes` to `0`. If your task creator leaves that field unset, start the worker with `--idle-on-complete 0s`. A nonzero task-level value overrides `--idle-on-complete 0s`.

### Start the worker and route the run

Add this script to the job your orchestrator starts. `CI_JOB_ID` must be unique for each job. This example relies on the task-level idle timeout being unset, so the worker flag sets it to zero.

```bash title="run-agent.sh"
#!/usr/bin/env bash
set -euo pipefail

: "${WARP_API_KEY:?Set WARP_API_KEY in the job environment}"
: "${CI_JOB_ID:?Set CI_JOB_ID to a unique job identifier}"

worker_id="external-${CI_JOB_ID}"

oz-agent-worker \
  --worker-id "$worker_id" \
  --backend direct \
  --one-shot \
  --idle-on-complete 0s &
worker_pid=$!

trap 'kill "$worker_pid" 2>/dev/null || true' EXIT

oz agent run-cloud \
  --host "$worker_id" \
  --prompt "Run the test suite, fix failures, and open a pull request."

wait "$worker_pid"
trap - EXIT
```

The run can enter the queue before the worker connects. Warp assigns the run after the matching worker ID is online, as long as the run has not reached its claim deadline. Use Direct backend [setup and teardown commands](/platform/self-hosting/managed-direct/#setup-and-teardown-commands) to prepare and clean up the allocated host.

## Using the Command backend

Use the Command backend when your runtime already owns job creation and cleanup. The worker sends each assigned task to `dispatch_command` as JSON on standard input. Exit code `0` means the runtime durably accepted the task; a nonzero exit or dispatch timeout fails it.

The public [`command-backend` example](https://github.com/warpdotdev/oz-agent-worker/tree/main/examples/command-backend) includes Python dispatch and cancellation scripts for an HTTP runtime. Copy and adapt those scripts, then configure the worker:

```yaml title="worker.yaml"
worker_id: "external-runtime"
backend:
  command:
    dispatch_command: "python3 /opt/warp/dispatch.py"
    cancel_command: "python3 /opt/warp/cancel.py"
    dispatch_timeout: "60s"
    environment:
      - name: OZ_DISPATCH_URL
        value: "https://runtime.internal.example.com/agent-runs"
      - name: OZ_CANCEL_URL
        value: "https://runtime.internal.example.com/agent-runs/cancel"
      - name: OZ_DISPATCH_AUTH_HEADER
```

Supply the runtime credential and Warp API key through your secret manager, then start the worker:

```bash
export OZ_DISPATCH_AUTH_HEADER="Bearer YOUR_RUNTIME_TOKEN"
export WARP_API_KEY="YOUR_SELF_HOSTED_WORKER_API_KEY"

oz-agent-worker --config-file worker.yaml
```

Your dispatch implementation must start the supplied `base_args` with the task environment, image, and sidecars from the payload. Keep the payload out of logs because it contains task credentials. After the CLI exits, the external runtime must run `oz harness-support --run-id RUN_ID report-shutdown` so Warp receives the terminal state. Set `RUN_ID` to the `run_id` field from the dispatch payload; the public [`command-backend` example](https://github.com/warpdotdev/oz-agent-worker/tree/main/examples/command-backend) shows this shutdown flow.

The worker does not wait for the remote agent to finish. `max_concurrent_tasks` limits concurrent dispatch calls, not agents running in the external runtime. Configure the external runtime's capacity separately.
