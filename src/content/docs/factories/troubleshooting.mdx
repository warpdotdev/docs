Fix problems with factory setup, event routing, and runs. Use the {VARS.FACTORY_WEB_APP} to inspect work, or fetch network diagnostics through the API.

## Setting up a factory

### You can't create or configure a factory

**Cause:** Creating a factory requires a team or workspace admin role, or the team-level Warp Factories Editor role. Configuring an existing factory requires its Editor or Admin role.

**Fix:** Ask a team or workspace admin to set your team-level Warp Factories role to Editor. To configure an existing factory, ask an Admin for that factory to set your role to Editor. See [factory roles and permissions](/factories/infrastructure-and-security/#factory-roles-and-permissions).

### A repository doesn't appear in the picker

**Cause:** The code host connection doesn't cover the repository.

**Fix:**

1. Confirm the connection includes the repository and the intended organization or group. See the [GitHub](/factories/integrations/github/) and [GitLab](/factories/integrations/gitlab/) integration guides for how each connection is scoped.
2. If you can't update it yourself, ask a GitHub organization owner, a GitLab group owner, or a Warp team admin to extend the connection.

<span id="setup-stops-at-an-agent-limit" />

### Setup stops at a worker limit

**Cause:** Your team's plan limits how many factory workers it can run.

**Fix:**

1. Ask a team admin to confirm the team's capacity.
2. If the team needs more workers, [contact sales](https://www.warp.dev/contact-sales).

### The web app still shows the setup wizard after your agent created a factory

**Cause:** Completing setup through [Factory MCP](/factories/factory-mcp/) doesn't update a {VARS.FACTORY_WEB_APP} page that's already open in your browser.

**Fix:** Refresh the page. Once your account has a factory, the web app opens it instead of the setup wizard. The factory link your agent shares at the end of setup opens the same place.

## Work isn't starting

### An event that should start work doesn't

**Cause:** A disabled or missing automation, a connection that doesn't cover the source, an account-linking requirement, or a filter mismatch can prevent work from starting.

**Fix:**

1. In the factory dashboard's **Automations** view, confirm an enabled automation exists for the event you sent. After saving changes, send a new matching event.
2. Confirm the source is connected to *this* factory. A workspace-level connection alone doesn't attach the provider to every factory.
3. Check that the installation or connected account can access the event's repository, project, or channel. Complete any administrator approval or account-linking prompt from the provider.
4. Check every filter, including the options under **More filters**. Filters combine with AND, so one mismatched repository, label, author, or state stops routing. GitHub also skips bot events by default. See [how automation matching works](/factories/automations/#how-matching-works).
5. Open the factory's [Runs page](/factories/factory-dashboard/#inspect-runs) and any work item already linked to the source thread, issue, or pull request. A follow-up can continue existing work rather than create a new work item. If a run exists but is waiting or failing, use [run troubleshooting](#runs-and-work-items) instead.

Then check the causes specific to where the work came from:

| Source | Common causes |
| --- | --- |
| [Slack](/factories/integrations/slack/#troubleshooting-and-reconnection) | The app isn't in the channel, installation is pending admin approval, or your Slack account isn't linked to a Warp team member |
| [Microsoft Teams](/factories/integrations/teams/#troubleshooting) | The app isn't added to the Teams team, the channel isn't configured, the sender isn't in the install's Microsoft 365 organization, or your Microsoft account isn't linked to Warp |
| [GitHub](/factories/integrations/github/#troubleshooting) | The app installation doesn't cover the repository, label routing doesn't match, or the event came from a bot |
| [GitLab](/factories/integrations/gitlab/#troubleshooting) | The mention was an edit rather than a new comment, or your plan doesn't include the group webhooks that deliver events |
| [Linear](/factories/integrations/linear/#troubleshooting) | The agent session needs a linked Warp account, or teams and filters don't match |
| [Jira](/factories/integrations/jira/#troubleshooting) | The Warp app isn't connected to your workspace, the person starting the session needs a linked account, or project and keyword filters don't match |
| [Custom webhooks](/factories/webhooks/#troubleshooting) | The delivery was rejected or deduplicated (check the webhook's **Recent deliveries**), no enabled automation selects the webhook, or the payload filter doesn't match |

If a new matching event still doesn't reach the factory, [contact support](https://docs.warp.dev/support-and-community/troubleshooting-and-support/sending-us-feedback/). Include the factory and automation links, the source event link, its timestamp and time zone, and any run link or error message.

### One action starts two runs

**Cause:** Two automations match the same event — commonly an app-mention trigger and a channel-message trigger pointed at the same place.

**Fix:** Narrow or remove one of the overlapping triggers so a single path owns each kind of request. See [how matching works](/factories/automations/#how-matching-works).

## Runs and work items

### You need to stop a run

**Fix:** Open the run on the factory's [Runs page](/factories/factory-dashboard/#inspect-runs) and click **Stop run**. It takes effect immediately, with no confirmation prompt.

### A work item looks stuck

**Cause:** The factory is often waiting on a person rather than failing. By default it pauses for spec approval, for answers to clarifying questions, and at the pull request.

**Fix:**

1. Open [Home](/factories/factory-home/) and click **Waiting on you** to find a question, spec review, or PR review tied to the work item.
2. Open the item to read the conversation or details and respond to the request. Click **View run details**, where available, to inspect the run.
3. If the run is still active, you can steer it directly. See [Cloud agent session sharing](/platform/viewing-cloud-agent-runs/).

### No pull request appears

**Cause:** The factory can't push, or the work never reached implementation.

**Fix:** Inspect the run's stage and assigned worker. Confirm its Blueprint can transition to implementation, any required gate has an answer, and the worker has write access to the target repository. Branch protection rules apply to everything the factory pushes.

### A run finishes without useful work

**Cause:** The worker stopped early because of missing access, missing
funding, a blocked host, a waiting gate, or instructions that ended the task
without opening a change.

**Fix:**

1. Open the run on the factory's
   [Runs page](/factories/factory-dashboard/#inspect-runs). Read the timeline
   for auth errors, insufficient usage, blocked network hosts, or a stage
   that never left planning.
2. Confirm shared team usage covers the run. Factory runs do not use a
   personal allowance. See
   [funding factory runs](/support-and-community/plans-and-billing/plans-pricing-refunds/#funding-factory-runs)
   and
   [insufficient usage recovery](/factories/api-and-sdk/troubleshooting/errors/insufficient-credits/#factory-runs).
3. Confirm the worker's harness can authenticate. Warp-hosted models need a
   funded shared balance. Claude Code, Codex, and Pi need a valid
   [team-owned auth secret](/factories/harnesses/authentication/). Consumer
   AI subscriptions are not valid factory credentials.
4. Confirm the GitHub App installation still covers the target repository and
   can push branches and open pull requests. See
   [GitHub push failures](/factories/integrations/github/#an-agent-cant-push-a-branch-or-open-a-pull-request).
5. Open [Home](/factories/factory-home/) with **Waiting on you** selected.
   Answer any pending question, spec review, or PR review, then start a new
   request if the original run already ended.
6. If the run shows `network/egress_blocked` diagnostics, follow
   [network requests fail during a run](#network-requests-fail-during-a-run).

### Setup or resume fails with a GitHub error

**Cause:** The factory can't use the GitHub App installation for the selected
repositories, or the definition sync can't read the connected repository.

**Fix:**

1. Confirm the Warp GitHub App installation covers every repository the
   factory lists. Organization owners can extend or reinstall the app from
   [GitHub's installation settings](https://github.com/settings/installations).
2. Confirm your Warp account is linked when the flow asks for GitHub account
   connection, and that you still belong to the factory's Warp team.
3. For a GitHub-backed definition, confirm the production branch is reachable
   and the latest apply or sync succeeded. Invalid definition changes keep
   the last valid definition. See
   [validate a definition](/factories/factory-as-code/#validate-a-definition).
4. Retry the setup or resume action after fixing access. If it still fails,
   [contact support](https://docs.warp.dev/support-and-community/troubleshooting-and-support/sending-us-feedback/)
   with the factory link, repository names, and the exact error text.

### You need to continue a finished or failed run

**Cause:** A stopped, failed, or completed run does not keep accepting new
work the way an open conversation might.

**Fix:** Open the work item or source thread and send a follow-up that your
automations accept, or start a new request with **New Chat** and the same
factory selected. For an active sandbox, open **View worker** from the run
page and steer the
[shared agent session](/platform/viewing-cloud-agent-runs/) while it remains
available. After the sandbox shuts down, use a new follow-up or new request
rather than expecting the finished run to resume in place.

### A prompt change does not change the workflow

**Cause:** The Blueprint's stage procedures and routing take precedence over stage lists in worker prompts.

**Fix:** Edit the stage's `prompt`, `to`, or `gates` in the [Blueprint definition](/factories/factory-as-code/#blueprint), then validate and apply it. Start new test work; replies to existing work keep that run's selected Blueprint.

### Network requests fail during a run

**Cause:** A factory or worker [network policy](/factories/factory-as-code/#networkpolicy) blocks hosts outside its allowed set. This can prevent package downloads, API calls, or inference requests.

**Fix:**

1. Fetch diagnostics for the affected worker run through the {VARS.WARP_PLATFORM_API}. Replace `RUN_ID` with its `run_id` from `GET /agent/runs`, not the factory or work item ID. For authentication, see the [API reference](https://docs.warp.dev/api). Your account must have access to the run.

   ```http
   GET https://app.warp.dev/api/v1/agent/runs/RUN_ID/diagnostics
   ```

   To include the same `diagnostics` array alongside the full run details instead, set `include_diagnostics=true`:

   ```http
   GET https://app.warp.dev/api/v1/agent/runs/RUN_ID?include_diagnostics=true
   ```

   Run details omit `diagnostics` by default.

2. Find entries with `code` set to `network/egress_blocked`. For example, the diagnostics endpoint returns:

   ```json
   {
     "diagnostics": [
       {
         "code": "network/egress_blocked",
         "message": "Network access to packages.example.com blocked",
         "data": {
           "blocked_host": "packages.example.com"
         },
         "timestamp": "2026-10-28T15:00:00Z",
         "created_at": "2026-10-28T15:00:02Z"
       }
     ]
   }
   ```

   `data.blocked_host` identifies the blocked hostname or IP address. The optional `timestamp` is when the blocked request occurred; the optional `created_at` is when the diagnostic was recorded. Diagnostics are warnings, not the run's outcome. The `state` field in run details reports that outcome.

3. If the run needs that host, add it to `allowedHosts` in the factory or worker policy. Review `deniedHosts` at both scopes and remove any conflicting entry: a denial overrides an allowance, including a built-in policy. [Apply the definition change](/factories/factory-as-code/#where-the-definition-lives), start a new run, and confirm the request succeeds.

If an opted-in run-details response omits `diagnostics`, use the dedicated diagnostics endpoint. An empty `diagnostics` array means no diagnostics were returned; it doesn't prove that every host is reachable. Check the failed command's output for other causes, and use the [API error reference](/factories/api-and-sdk/troubleshooting/errors/) for authentication or access errors.
