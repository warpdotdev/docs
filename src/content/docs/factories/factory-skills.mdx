A skill gives an agent a repeatable procedure, such as a security review or incident runbook. In a factory, these configured agents are called [workers](/factories/factory-agents/). Factory skills extend their instructions without requiring changes to their prompts.

In a [Blueprint](/factories/blueprints/), the stage prompt names the work and the skills to use. Keep reusable check commands in a skill; keep stage handoffs, transitions, and gates in the Blueprint. A skill does not replace the workflow's stage order.

## Skill sources in a factory

<span id="factory-role-and-integration-skills" />
<span id="warp-provided-platform-bundled-skills" />

A factory run can use skills from three sources:

* **Role and integration skills** - Default workers have GitHub skills for repository work. The foreman also has a Slack skill. Choosing Linear or Jira during setup gives relevant workers the tracker's skill and instructions. These skills come from roles and integrations, not files in your definition.
* **Warp-provided skills** - Bundled capabilities include `oz-platform` for cloud agents, `factory-files` for factory definitions, and `factory-mcp` for sending work to factories.
* **Custom skills** - Team-owned `SKILL.md` files live in the factory definition or are referenced from another location in the same repository or an external repository. They are shared across the factory or scoped to one worker and extend the built-in skills rather than replacing them.

<span id="attribute-team-owned-skill-usage" />

For bundled skill IDs and how to attribute team-owned skill usage, see [Skill actions in conversation data](/factories/api-and-sdk/#skill-actions-in-conversation-data).

## When to add a custom skill

Add a custom skill for procedures the built-in skills don't cover. For example:

* Run required tests or lint checks.
* Follow incident-response or triage runbooks.
* Apply a security or compliance review checklist.
* Teach a custom worker its job. Custom workers have no built-in skills.

Skills provide instructions, not access to tools or repositories. If a procedure requires credentials or an MCP connection, configure the worker's [secrets](/factories/secrets/) and [MCP servers](/factories/mcp/) through its [settings](/factories/factory-agents/configuration/#edit-agent-settings-and-instructions). For how that access is limited, see [credential boundaries](/factories/infrastructure-and-security/#credential-boundaries).

## Add or edit a skill

Configure custom skills in the factory's [definition](/factories/factory-as-code/#directory-structure), not its worker settings. You need permission to edit that definition.

To add or update a custom skill:

1. Open the definition where it's managed:
   * **Warp-managed** - In the web app sidebar, expand your factory and click **Factory definition**.
   * **GitHub-backed** - Open the connected definition repository. See [Where the definition lives](/factories/factory-as-code/#where-the-definition-lives).
2. Create or open the skill file for the scope you need:
   * **Every worker** - `skills/<skill-name>/SKILL.md`, for shared procedures such as repository conventions.
   * **One worker** - `workers/<worker-name>/skills/<skill-name>/SKILL.md`, for a role-specific procedure such as a security review. If the definition uses `agents/`, use `agents/<worker-name>/skills/<skill-name>/SKILL.md` instead. Keep the existing root, even when adding a skill.

   Replace `<skill-name>` with the skill's directory name and `<worker-name>` with the worker's directory name.

   In a `workers/` tree, this shares repository conventions with every worker and gives only the foreman an incident-triage skill:

   ```text
   skills/
     repository-conventions/
       SKILL.md
   workers/
     foreman/
       skills/
         incident-triage/
           SKILL.md
   ```
3. Write or update the skill's instructions, name, and description. See [Skill file format](/agents/capabilities/skills/#skill-file-format) for frontmatter and [Skill arguments](/agents/capabilities/skills/#skill-arguments) for parameters.
4. Apply the change:
   * **Warp-managed** - Save the definition. Warp validates and commits it.
   * **GitHub-backed** - Open a pull request. The factory's [pull request checks](/factories/factory-as-code/#pull-request-checks) validate the change, and merging to the production branch applies it.

For an example of shared and agent-specific skills, see [`sdlc-issue-to-pr`](https://github.com/warpdotdev/warp-factory-examples/tree/484a8b431d79407a4623b57503be1dd983080cf5/examples/sdlc-issue-to-pr) in [warp-factory-examples](https://github.com/warpdotdev/warp-factory-examples).

## Reference existing skills

To reuse skills without copying them, create a `.yaml` or `.yml` reference file directly in `skills/` for every worker. For one worker, use `workers/<worker-name>/skills/` in a `workers/` tree or `agents/<worker-name>/skills/` in an `agents/` tree. Set `source` to the repository and `include` to the skills to load, then apply the definition change as described above.

The source can be the repository containing your definition or an external repository. Pin it to a full commit SHA to keep using a particular version of the skill and its supporting files. See [Skill reference files](/factories/factory-as-code/#skill-reference-files) for same-repository, external-repository, and SHA-pinned examples.

## Improve a skill from observed failures

A failed run can reveal a missing instruction in a skill. For example, a startup skill tells the worker to launch an app but omits a command to build a UI package the app depends on. The worker follows the instructions, but the app fails to start.

1. Inspect the failed command and repository build instructions to confirm the cause. If the instructions are correct but a required service or permission is unavailable, address that problem instead of changing the skill.
2. In the existing startup skill file, add the missing build command before the app-start command. Describe how to confirm that the app is ready.
3. Manually follow the revised startup instructions from a clean checkout of the application repository. Once the app loads, complete a small task, such as verifying that a button copies the expected URL.
4. Review the changed instructions and test results. Apply the approved change through the [definition's save or merge process](#add-or-edit-a-skill).
5. Start a new factory run with the same small task. Check that the worker loads the revised skill, follows the added build step, and completes the task.

Apply the same testing and review to automated proposals. When a Scorer with [Self-improvement](/factories/measure-and-improve/self-improvement/) enabled flags a recurring failure, a follow-up run can propose a skill change in a pull request for your review.
