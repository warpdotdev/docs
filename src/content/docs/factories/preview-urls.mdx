Preview URLs let you try an app running in a Warp Factories sandbox from your own browser. Ask the agent for a preview of its changes, then open the returned link to test the app or share it with your team.

A preview connects to the development server in the run's sandbox, not a production deployment. For example, preview a changed checkout page before reviewing its pull request. Screenshots and recordings show what an agent tested; a preview lets you interact with the app yourself.

## Requirements

* A factory run on a supported Warp-hosted sandbox. Namespace sandboxes support previews. Docker Sandboxes, local runs, and self-hosted workers don't support them.
* The app's dependencies, startup instructions, and any required services or test data available in the sandbox. Configure these through [runners](/factories/runners/) and [factory repositories and setup](/factories/factory-as-code/).
* Preview URLs enabled for both the owning workspace and team. An administrator can [change this policy](#controlling-preview-availability).

The Preview URLs MCP server is provided to cloud runs automatically; you don't need to add a custom MCP server or create a separate API key to request a browser preview. This works with the Warp Agent and third-party harnesses when the run has the preview tools.

Use an app port from `1024` to `65535`, excluding Warp's reserved ports `9277`–`9282` and `29777`.

## Access and sharing boundaries

Every preview requires Warp authentication. Copying the URL doesn't grant access, and there is no public, anonymous visibility option.

| Scope | Who can open the preview | Who can edit or delete it directly |
| --- | --- | --- |
| Private (`PRIVATE`) | The run's user creator and admins of the owning team or its native workspace | The same people |
| Team (`TEAM`) | The creator, those admins, and members of the team that owns the run | The creator and those admins |

Private is the default for a run created by a person unless you request team access. Runs created by service accounts require Team scope; they can't have private previews. Other workspace members don't gain access merely by belonging to the workspace.

:::caution
Preview visibility controls who can open the app, not who can steer its agent. Anyone allowed to send follow-ups to the run can ask the agent to modify or delete its previews, including private previews. Review [factory follow-up restrictions](/factories/factory-as-code/#restrictfollowupstostarter) separately.
:::

## Requesting a preview

1. In your factory conversation, ask the agent to start the app and create a preview. Include the page and data you want to try. For example:

   > Start the app using this repository's development instructions and create a private preview of the checkout page. Use only synthetic cart and customer data. Open the preview on the checkout route, and tell me when it expires. Don't deploy to production.

   The agent follows the repository's startup workflow, waits for the server to report that it's listening, and returns a labeled preview link with an expiration time. If the app needs credentials or services that aren't available, resolve that startup blocker before requesting the preview again.

2. Open the returned preview link in your browser. If prompted, sign in to Warp with an account authorized for that preview. App-specific authentication still applies after Warp sign-in.

3. Exercise the changed workflow. For the checkout example, add a synthetic item and confirm the checkout page shows the expected cart. A created link alone doesn't prove the app works.

Agents create previews when you explicitly ask or accept an offer. Asking for a preview doesn't also request Computer Use verification. To have the agent test the interface or capture evidence, request [Computer Use verification](/factories/use-cases/computer-use-verification/) separately.

## Finding and managing a preview

In the <a href={VARS.FACTORY_WEB_APP_URL}>{VARS.FACTORY_WEB_APP}</a>, open the producing run's conversation and its **Artifacts** tab. Under **Preview URLs**, open the labeled preview or copy its link. The entry shows its port, scope, and remaining time.

With direct management access from the [access table](#access-and-sharing-boundaries):

1. Open the preview's actions menu and click **Edit**.
2. Change the "Label," "Scope," or "Expires in" value. To share with teammates, choose **Team** in "Scope."
3. Click **Save**. When widening access to Team, confirm with **Save changes**.
4. Copy the link and send it to an authorized recipient. The URL stays the same after an edit. Each recipient signs in to Warp.

You can also ask the agent in the producing conversation:

> Rename the checkout preview to “Checkout review” and share it with the team that owns this run. Keep its current expiration.

Agent tools manage previews from their own current execution, not another run or an earlier execution.

### Expiration and sandbox lifetime

Previews expire one hour after creation by default. Before a preview expires, change "Expires in" in the editor or ask the agent for a new duration, such as “Set the checkout preview to expire 30 minutes from now.” The duration starts when the change is applied, not at the previous expiration time. The editor's **Maximum available** option is bounded by the sandbox's remaining lifetime.

A preview stops working when it expires, is deleted, or its sandbox shuts down. Extending a preview doesn't extend the sandbox's lifetime. An expired preview can't be revived. Start the app in a new supported run and request a new URL when the old sandbox is gone.

### Deleting a preview

In **Artifacts**, open the preview's actions menu, click **Delete**, then confirm **Delete**. Alternatively, ask its agent to delete that preview.

Deletion removes access to the URL but doesn't stop the development server or sandbox. Stop the app separately if you no longer need it.

## Calling a preview from an HTTP client

For programmatic access, use a [Warp API key](https://docs.warp.dev/agents/cli/oz-cli/api-keys/) belonging to a principal with access to the preview. Load the credential securely into `WARP_PREVIEW_CREDENTIAL` without printing it or placing it in chat. Set `PREVIEW_URL` to the returned preview origin, then run:

```bash
curl --header "X-Warp-Preview-Authorization: Bearer ${WARP_PREVIEW_CREDENTIAL}" \
  "${PREVIEW_URL}/path/to/endpoint"
```

Replace `/path/to/endpoint` with your app's endpoint. The preview proxy removes this credential header before forwarding the request. The ordinary `Authorization` header is reserved for your app's own authentication; it doesn't authenticate the preview.

Previews support HTTP/1.1 apps, including WebSockets, hot reload, and server-sent events. HTTP/2 and HTTP/3 aren't supported. Browser requests from another website can't use the preview's sign-in flow as cross-origin API authentication.

## Controlling preview availability

Workspace administrators control preview availability for the workspace and its teams. In the [Admin Panel](https://app.warp.dev/admin/), select the workspace or team, then open **Platform**. In the "Preview URLs" section, toggle **Enable preview URLs**.

Disabling previews permanently deletes active preview URLs in that scope. Confirm **Disable** only if you intend to revoke those links. Re-enabling the setting doesn't restore deleted previews. A team can't override a workspace-level disable.

Existing WebSocket connections can remain open after access is revoked. Stop the app or sandbox if you also need to terminate those connections.

## Troubleshooting

| Symptom | What to do |
| --- | --- |
| Preview URLs are disabled for the team or workspace | Ask an administrator to enable previews at both scopes. |
| Preview tools are missing, or the sandbox is unsupported | Request a new run on a supported Warp-hosted sandbox. A custom MCP configuration doesn't add sandbox support. |
| A preview already exists for the port | Reuse its existing link. Don't start a duplicate server on another port merely to get another URL. |
| The preview doesn't load | Ask the agent to inspect the app's startup logs and confirm the server is still listening on the previewed port. Check app dependencies and the reserved-port exclusions above. |
| A teammate can't open the link | Confirm they're signed in with an account on the owning team. Ask the creator or an authorized admin to change Private scope to Team. |
| The link returns a not-found page | Check access and expiration. An expired, deleted, inaccessible, or closed-sandbox preview isn't a usable link. Request a new preview when the sandbox is gone. |
| An expiration change exceeds the available lifetime | Choose a shorter duration or **Maximum available**. A preview can't outlive its sandbox. |
