import { VARS } from '@data/vars';

Use an existing CI system, Kubernetes controller, or internal scheduler to allocate compute while the {VARS.WARP_AUTOMATION_PLATFORM} routes and tracks each run. Choose one-shot Direct when your scheduler starts a self-hosted runner for each job. Choose the Command backend when a connected self-hosted runner should hand tasks to an existing runtime.

## Choosing a pattern

| Pattern | External orchestrator responsibility | Self-hosted runner behavior | Use when |
| --- | --- | --- | --- |
| One-shot Direct | Allocates a host, starts a self-hosted runner, and creates a run for its unique self-hosted runner ID | Runs one accepted task on the allocated host, then exits | Your scheduler creates a VM, pod, or CI runner for each job |
| Command backend | Provides a command or API that accepts a task and owns its compute lifecycle | Stays connected and invokes the dispatch command for each task | Your runtime already exposes a job API, queue, or scheduler |

Both patterns use the managed architecture: Warp accepts triggers and routes runs, while your orchestrator owns compute allocation.

## Prerequisites

* Managed self-hosting access, network connectivity, and credentials. See the [shared managed prerequisites](/factories/self-hosting/#managed-prerequisites).
* `oz-agent-worker` installed from a [published release](https://github.com/warpdotdev/oz-agent-worker/releases).
* For one-shot Direct, the {VARS.WARP_AGENT_CLI} on the allocated host.
* For the Command backend, the tools used by the dispatch and cancellation commands.

## Using one-shot Direct

Start a self-hosted runner using the Direct backend and `--one-shot` when your scheduler allocates one host per job. One-shot mode accepts one task, forces `max_concurrent_tasks` to `1`, and exits after that task succeeds, fails, or is cancelled. If no task arrives, the self-hosted runner stays connected until your orchestrator stops it.

Use a unique self-hosted runner ID for every job so another self-hosted runner cannot claim the run.

### Configure the completion timeout

The agent process normally remains available for follow-up prompts for 45 minutes after a conversation completes. Timeout settings use this precedence:

1. The task-level `config.idle_timeout_minutes` value, including defaults applied by the task creator. Runs created directly through the [Agent API](/api) use 10 minutes when this field is omitted.
2. The self-hosted runner's `idle_on_complete` setting or `--idle-on-complete` flag when the task reaches the self-hosted runner without a task-level value. Unlike a direct Agent API request, `oz agent run-cloud` uses the CLI task-creation path, which does not apply the API's 10-minute default and leaves this value unset.
3. The 45-minute default when neither value is set.

For a job created directly through the Agent API that must exit immediately, set `config.idle_timeout_minutes` to `0`. If the task reaches the self-hosted runner without this field, start the self-hosted runner with `--idle-on-complete 0s`. A task-level value overrides `--idle-on-complete 0s`.

### Start the self-hosted runner and route the run

Add this script to the job your orchestrator starts. `CI_JOB_ID` must be unique for each job.

This example uses one Default Service Account agent key for both the self-hosted runner and `run-cloud`. When those actions run in different processes, use a self-hosted runner key for the self-hosted runner and an agent key for the run creator.

```bash title="run-agent.sh"
#!/usr/bin/env bash
set -euo pipefail

: "${WARP_API_KEY:?Set WARP_API_KEY in the job environment}"
: "${CI_JOB_ID:?Set CI_JOB_ID to a unique job identifier}"

worker_id="external-${CI_JOB_ID}"

oz-agent-worker \
  --worker-id "$worker_id" \
  --backend direct \
  --one-shot \
  --idle-on-complete 0s &
worker_pid=$!

trap 'kill "$worker_pid" 2>/dev/null || true' EXIT

oz agent run-cloud \
  --host "$worker_id" \
  --prompt "Run the test suite, fix failures, and open a pull request."

wait "$worker_pid"
trap - EXIT
```

**Expected outcome:** The run appears in the dashboard, the self-hosted runner accepts it, and the self-hosted runner exits when the conversation completes. The run can enter the queue before the self-hosted runner connects. If no matching self-hosted runner claims it, Warp eventually fails the run. Use Direct backend [setup and teardown commands](/factories/self-hosting/managed-direct/#setup-and-teardown-commands) to prepare and clean up the allocated host.

## Using the Command backend

Use the Command backend when your runtime already owns job creation and cleanup. The self-hosted runner sends each assigned task to `dispatch_command` as JSON on standard input. Exit code `0` means the runtime durably accepted the task; a nonzero exit or dispatch timeout fails it.

The public [`command-backend` example](https://github.com/warpdotdev/oz-agent-worker/tree/main/examples/command-backend) includes Python dispatch and cancellation scripts for an HTTP runtime. Copy and adapt those scripts, then configure the self-hosted runner:

```yaml title="worker.yaml"
worker_id: "external-runtime"
backend:
  command:
    dispatch_command: "python3 /opt/warp/dispatch.py"
    cancel_command: "python3 /opt/warp/cancel.py"
    dispatch_timeout: "60s"
    environment:
      - name: OZ_DISPATCH_URL
        value: "https://runtime.internal.example.com/agent-runs"
      - name: OZ_CANCEL_URL
        value: "https://runtime.internal.example.com/agent-runs/cancel"
      - name: OZ_DISPATCH_AUTH_HEADER
```

Supply the runtime credential and Warp API key through your secret manager, then start the self-hosted runner:

```bash
export OZ_DISPATCH_AUTH_HEADER="Bearer YOUR_RUNTIME_TOKEN"
export WARP_API_KEY="YOUR_SELF_HOSTED_WORKER_API_KEY"

oz-agent-worker --config-file worker.yaml
```

Your dispatch implementation must handle the task payload as follows:

* **Start command** - Run the supplied `base_args` with `env`.
* **Runtime configuration** - Use `docker_image` and `sidecars` to prepare the runtime.
* **Task payload** - Keep it out of logs because it contains task credentials. See the example's [task payload reference](https://github.com/warpdotdev/oz-agent-worker/tree/main/examples/command-backend#what-the-worker-hands-the-script-stdin) for each field.
* **Shutdown report** - After the CLI exits, run `oz harness-support --run-id RUN_ID report-shutdown` so Warp receives the terminal state. Set `RUN_ID` to the `run_id` field from the dispatch payload.

The self-hosted runner does not wait for the remote agent to finish. Stopping or restarting the self-hosted runner does not cancel tasks that the external runtime already accepted. `max_concurrent_tasks` limits concurrent dispatch calls, not agents running in the external runtime. Configure the external runtime's capacity separately.
