Start a self-hosted worker with the default Docker backend and route a test run to it. The {VARS.WARP_AUTOMATION_PLATFORM} routes the run, and your worker provides the compute.

---

## Prerequisites

* Managed self-hosting access and network connectivity. See the [shared managed prerequisites](/factories/self-hosting/#managed-prerequisites).
* A [self-hosted worker API key](/agents/cli/oz-cli/api-keys/#creating-a-self-hosted-worker-api-key).
* A Warp account on the worker's team with permission to create runs, for the test below.
* A Linux machine with a rootful Docker daemon and GNU `stat`.
* The {VARS.WARP_AGENT_CLI} on the machine that will route the test run. See [Installing the CLI](/agents/cli/oz-cli/#installing-the-cli).

For macOS or Windows, use the [Homebrew](/factories/self-hosting/managed-docker/#option-2-homebrew) or [release binary](/factories/self-hosting/managed-docker/#option-3-github-releases-binary) setup instead.

## Run your first self-hosted agent

_~10 minutes_

### 1. Export your worker API key

Export the self-hosted worker key in the terminal that will start the worker. Run creation uses your login separately:

```bash
export WARP_API_KEY="YOUR_SELF_HOSTED_WORKER_API_KEY"
```

### 2. Start the worker

On the Linux host, run the `oz-agent-worker` container and mount the Docker socket so the worker can spawn task containers. Choose any `--worker-id` meaningful for your team — you'll use this value to route tasks to this worker.

```bash
export DOCKER_SOCKET_GID="$(stat -c '%g' /var/run/docker.sock)"

docker run \
  --group-add "$DOCKER_SOCKET_GID" \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e WARP_API_KEY="$WARP_API_KEY" \
  warpdotdev/oz-agent-worker --worker-id "my-worker"
```

**Expected outcome:** The worker connects to the {VARS.WARP_AUTOMATION_PLATFORM} and begins listening for tasks. You should see log output confirming the connection (something like `Connected to Oz` / `Waiting for tasks`).

:::caution
For production deployments, pin to a specific image digest (e.g., `warpdotdev/oz-agent-worker@sha256:...`) instead of the `latest` tag.
:::

### 3. Route a run to your worker

In a separate terminal with the {VARS.WARP_AGENT_CLI}, clear the worker key and sign in as yourself. Keep the worker running in its original terminal:

```bash
unset WARP_API_KEY
oz login
```

Complete sign-in using the URL the CLI prints. Route a team-owned run with `--team` and pass the worker ID with `--host`. If you belong to multiple teams, choose the worker's team:

```bash
oz agent run-cloud --team \
  --prompt "List the files in the current directory" \
  --host "my-worker"
```

For unattended factory submissions, use a separate [foreman agent key](/agents/cli/oz-cli/api-keys/#finding-the-factorys-foreman) with [factory endpoints](/factories/factory-api/), not the worker key.

**Expected outcome:** The {VARS.WARP_AUTOMATION_PLATFORM} accepts the task, routes it to your worker, and the worker spawns a Docker container to execute the agent. You'll see the run appear in the <a href={VARS.WEB_APP_URL}>{VARS.DASHBOARD}</a> with status moving from `QUEUED` → `INPROGRESS` → `SUCCEEDED`.

### 4. Verify the run

Open the <a href={VARS.WEB_APP_URL}>{VARS.DASHBOARD}</a>, find the new task, and confirm the session transcript shows the agent running against your worker. You can attach to the session at any time via [Agent Session Sharing](/agents/local-agents/session-sharing/) to monitor or steer it.

## Troubleshooting

**Worker won't start**\
Verify Docker is running (`docker info`) and that the daemon platform is `linux/amd64` or `linux/arm64`. Musl-based (Alpine) worker hosts are not supported.

**Worker won't connect**\
Verify the worker key has not expired and belongs to the correct team. Ensure the machine meets the [network requirements](/factories/self-hosting/security-and-networking/#network-requirements). Increase log verbosity with `--log-level debug` to see connection details.

**Task stays queued and never runs**\
Confirm the `--host` value you passed to `oz agent run-cloud` matches your `--worker-id` exactly (case-sensitive). Check that the worker's team matches the team creating the task.

For more, see [Troubleshooting](/factories/self-hosting/troubleshooting/).
