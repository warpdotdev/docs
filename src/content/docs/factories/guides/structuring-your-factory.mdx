A factory boundary is the set of repositories one factory works in, together with the agents, skills, intake, credentials, and approvals that apply there. It decides what a run can see and change and who signs off on the result, so choose it by how your code is owned and shipped, not by how many repositories you have. For example, a web app whose frontend and backend ship together belongs in one factory even when they live in two repositories, while two products that share a monorepo but have different owners can each get their own.

The rule of thumb from [sizing a factory](/factories/#sizing-a-factory) still holds: group the repositories that ship together, keep separate products apart, and specialize with [custom agents](/factories/factory-agents/creating-custom-agents/) and [skills](/factories/factory-skills/) rather than splitting one codebase by team or task.

## What a boundary decides

* **Repositories** - The [`repositories`](/factories/factory-as-code/#repositories) list is what every run checks out and what the agents are told to work in. Access itself comes from the code host connection and its permissions, so narrow the installation as well as the list. See [GitHub permissions](/factories/integrations/github/#permissions).
* **Agents and skills** - The foreman, the default agents, and any custom agents share the factory's [skills](/factories/factory-skills/), so repository conventions and commands are written once per factory.
* **Intake** - [Automations](/factories/automations/) filter events by repository, label, team, or channel and send them to this factory's foreman. When two factories watch the same event, each starts its own run.
* **Credentials** - Repository identity, [secrets](/factories/secrets/), and MCP servers are configured per factory and per agent. Automation filters don't narrow access. See [credential boundaries](/factories/infrastructure-and-security/#credential-boundaries).
* **Approvals** - Spec approval is policy in the foreman's instructions. Merging is enforced by each repository's branch protection and required reviews, and the factory never merges. See [human decision points and permissions](/factories/factory-agents/#human-decision-points-and-permissions).
* **Operations** - A factory has one default [runner](/factories/runners/), which agents can override, and one [dashboard](/factories/factory-dashboard/) for cost, Scorers, and pull request metrics. Every stack inside the boundary has to fit that setup, and their results are measured together.

## Questions that set the boundary

Work through the questions in order. The first answer that lands in the right-hand column usually settles it.

| Question | Keep in one factory when | Use separate factories when |
| --- | --- | --- |
| **Ownership** - Who reviews and merges? | One team reviews and merges changes across all of the code | Different teams own the code and don't review each other's pull requests |
| **Coupling** - Does the code ship together? | A change often touches several of the repositories, and they deploy together or against a shared contract | The repositories change independently, and a change that spans them is rare |
| **Permissions** - Who may see and change the code? | Everyone who sends work to the factory may reach every repository in it | Some code needs credentials, secrets, or MCP access that other work must not receive |
| **Approvals** - Where do people sign off? | One spec policy and one merge process fit all of the code, with escalation rules for the exceptions | Part of the code needs its own approval path that an escalation rule can't express |
| **Operating needs** - What does a run need to build and test? | One runner image and setup serve every repository, and one dashboard is the right place to measure | Stacks need different images, operating systems, or hosts, or their cost and quality must be measured separately |

Repository count isn't on the list. One factory can hold several repositories, and one repository can host several products. A product with its own owners and approval path can have its own factory even when it shares a repository with others.

## What this looks like for your shape

Each page below applies the questions to a common codebase shape and links a complete definition you can copy from [warp-factory-examples](https://github.com/warpdotdev/warp-factory-examples):

* [Setting up a factory for a web application](/factories/guides/web-application-factory/) - Frontend and backend work in one factory, with the app and its tests set up so changes can be verified in a browser.
* [Setting up a factory for a monorepo](/factories/guides/monorepo-factory/) - One product inside a shared repository, with checks on shared packages and escalation to their owners.
* [Setting up a factory for microservices](/factories/guides/microservices-factory/) - Related services grouped by contract and ownership, with runtime context and contract checks.
* [Coordinating changes across multiple repositories](/factories/guides/multi-repository-factory/) - One pull request per repository, linked together, with a merge order a person controls.

Factories shared by several teams, or operated by a platform team on behalf of others, add shared standards and routing responsibilities on top of these shapes.

## Set it up with a prompt

Paste this into a conversation with your factory's foreman (**New Chat** in the factory dashboard) or into a coding agent connected through [Factory MCP](/factories/factory-mcp/). Fill in the uppercase placeholders first.

```text title="Prompt"
Read https://docs.warp.dev/factories/guides/structuring-your-factory.md and
help me choose factory boundaries. My repositories are REPO_LIST. For each
one I will tell you which team owns and merges it, which repositories
deploy together or share a contract, and which need credentials that other
work must not receive.

Propose the factories to create. For each proposed factory, list its
repositories, the owning team, how work will enter it, who approves specs
and merges, what its runner must be able to build and test, and which
example to start from:
https://github.com/warpdotdev/warp-factory-examples/tree/main/examples/01-single-repo-quickstart
for one repository,
https://github.com/warpdotdev/warp-factory-examples/tree/main/examples/24-monorepo-product
for one product in a monorepo, or
https://github.com/warpdotdev/warp-factory-examples/tree/main/examples/25-related-services
for repositories that share a contract. Show me the proposal before you
create or change anything.
```

## Troubleshooting

* **The foreman declines or misplaces requests** - Work arrives for code the factory doesn't own, or a request doesn't say which repository or product it belongs to. Narrow intake with one label or filter per factory, and write the scope, directories, and owners into a shared skill so the foreman can place a request before dispatching it. The [monorepo factory](/factories/guides/monorepo-factory/) shows the pattern.
* **Pull requests wait on people outside the factory's team** - The boundary crosses ownership. Add an escalation rule that opens those pull requests as drafts with review requested from the owning team, or move that code into its own factory.
* **One event starts runs in two factories** - Both factories watch the same repository or channel with overlapping filters. Give each factory its own label, channel, or project filter so an event matches one automation. See [one action starts two runs](/factories/troubleshooting/#one-action-starts-two-runs).
* **Setup fails or takes most of the run** - One runner is carrying every stack in the factory. Scope setup commands to the code a run needs, give agents their own runners, or split the factory by operating needs. See [runners](/factories/runners/).
