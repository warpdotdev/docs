Use Warp Factories to group services that share a contract and an owner. Agents verify changes against contract files in the repositories rather than a live deployment.

Adapt the [`01-single-repo-quickstart`](https://github.com/warpdotdev/warp-factory-examples/tree/main/examples/01-single-repo-quickstart) starter by adding the related repositories. The examples below use a Go API and a Node web app sharing `openapi.yaml`; replace their illustrative names, paths, and commands with yours.

## How a microservices factory is organized

Group services in one factory when they share an API, schema, or event contract, regularly need coordinated changes, and are reviewed by the same team. Use separate factories for services that change independently or have different owners, even if they communicate in production. See [factory boundaries](/factories/guides/structuring-your-factory/) for guidance.

Each run checks out all of the factory's repositories so the agents can examine the provider and consumers together:

* **Foreman:** Identifies which services the request affects.
* **Implement agent:** Updates the provider's contract first, then runs each service's checks and contract check, including the consumer's check against the provider's current `main`.
* **Review agent:** Checks that the provider and consumer changes agree.

This example allows only additive contract changes. For breaking changes, such as removing, renaming, or changing a field's type, the foreman explains what is needed instead and stops.

Runs start with repository checkouts, not deployed services. Verify changes using contract files and fixtures. If a test needs a dependency such as a database, start it in the sandbox with the repository's documented command. Warp-hosted Linux runners support Docker containers.

A change spanning services produces one pull request per repository. A person controls the merge order. See [coordinating changes across multiple repositories](/factories/guides/multi-repository-factory/).

| Part | Recommendation |
| --- | --- |
| Trigger | A maintainer applies `factory-ready` to an issue in any of the factory's repositories |
| Repositories | The services that share a contract and an owner; the foreman's instructions name the provider |
| Agents | Foreman, implement, and review; review only checks that the services agree |
| Runner | One Linux image that carries every service's toolchain, with a per-service dependency prefetch |
| Output | One pull request per changed service with its checks and contract-check results |

## Prerequisites

* A [factory](/factories/quickstart/) connected to [GitHub](/factories/integrations/github/) with access to every service repository.
* [Foreman, implement, and review agents](/factories/factory-agents/#the-default-agents) in the factory.
* A provider contract file, such as `openapi.yaml`, and contract checks in each repository. The provider checks its handlers against the contract. Each consumer regenerates its client and type-checks all call sites.
* Documented bootstrap and test commands for every service.

## Group related services

The factory's repository list is the group: the services whose contract and ownership match.

1. List the provider and its consumers in `factory.yaml`. This example has one of each. Add consumers that share the contract and reviewers.

   ```yaml title="factory.yaml"
   schemaVersion: v1alpha1
   name: related-services
   alias: Services
   repositories:
     - owner: acme
       name: api-service
     - owner: acme
       name: webapp
   agentDefaults:
     model: auto
     runner: linux-services
   ```

2. Define each repository's role in `agents/foreman/agent.md`:
   * Identify the contract provider and its consumers.
   * Instruct the foreman to identify which services a request affects, order changes from provider to consumer, and decline work outside the factory.
3. Create the `factory-ready` label in every service repository. GitHub labels are configured separately for each repository.
4. Configure the intake automation to match those repositories and the `factory-ready` label:

   :::note
   Use `issue_labeled` for issue labels and `pull_request_labeled` for pull request labels.
   :::

   ```yaml title="Intake trigger"
   triggers:
     - provider: github
       event: issue_labeled
       filter:
         repos: [acme/api-service, acme/webapp]
         labels: [factory-ready]
   ```

## Provide runtime context

1. Choose one runner image with every service's toolchain. Options include:
   * `warpdotdev/dev-go:1.23`, used below, with Go and Node.
   * `warpdotdev/dev-full:latest`, with every language in [Warp's prebuilt dev images](https://github.com/warpdotdev/oz-dev-environments).
   * Another public image with the required toolchains.
2. Add one dependency prefetch command per repository to the runner's `setupCommands`. Each command starts in `/workspace`, so change to the repository's directory before fetching dependencies.

   ```yaml title="runners/linux-services.yaml"
   description: >-
     One runner with Go and Node for the API and web app checkouts.
   setupCommands:
     - '(cd /workspace/api-service && go mod download) || echo "Warning: api-service prefetch skipped" >&2'
     - '(cd /workspace/webapp && npm ci) || echo "Warning: webapp prefetch skipped" >&2'
   instanceShape:
     vcpus: 4
     memoryGb: 8
   platform:
     os: linux
     arch: x86_64
     linux:
       dockerImage: warpdotdev/dev-go:1.23
   ```

   :::note
   A nonzero exit status from a setup command fails the sandbox. Each prefetch command logs a warning on failure so the implement agent can run the bootstrap command in every repository it changes.
   :::

3. Document each service's commands in `agents/implementer/agent.md`, or in a shared skill under `skills/` when there are several consumers. Include:
   * Bootstrap command.
   * Normal checks.
   * Contract check.
   * Contract file path.

   See [factory skills](/factories/factory-skills/) for the shared skill format.
4. Configure any access the service needs beyond its checkout:
   * [MCP servers](/factories/mcp/) for logs or error tracking when handling incidents.
   * [Factory secrets](/factories/secrets/) for private package registries.

   Skills describe how to use resources. Access comes from the agent's configuration.

## Verify against contracts and dependencies

1. Define the compatibility policy in `agents/foreman/agent.md`:
   * Change the provider first.
   * Allow only backward-compatible additions. Do not remove, rename, or change the types of existing fields or endpoints, or add required request fields.
   * For a breaking change, comment with an alternative, such as a versioned endpoint or coordinated deployment, and stop without creating a branch.

   Check that the deployed consumer tolerates the additions.
2. In `agents/implementer/agent.md`, require the provider's implementation checks:
   * Run bootstrap, retrying any failed dependency prefetch before testing. Report a blocker if bootstrap still fails.
   * Update the contract file before the handlers and their tests.
   * Run the normal checks and contract check.
   * Confirm that the contract diff contains only additions.

   For example, run `go build ./... && go test ./...`, your repository's contract check, and `git diff origin/main -- openapi.yaml` after fetching the default branch. Substitute its name if it isn't `main`.
3. Require consumer verification against both versions of the provider's contract:
   * Copy the provider branch's schema over the consumer's vendored copy.
   * Run `npm run lint && npm test` and `npm run contract-check`.
   * Run the contract check again using the provider's current `main` schema, then restore the branch's schema. Use your contract check's schema-path option, or replace its input file.
   * If the check against `main` fails because the consumer needs the new contract, record that result in the pull request as the reason the consumer merges second.
4. Define the cross-service review in `agents/reviewer/agent.md`. Require the review agent to confirm that:
   * The provider's contract and the consumer's vendored copy are identical.
   * The consumer uses the added fields with matching names and types.
   * The provider's contract diff contains only additions.

   Leave other judgments to a person.
5. Apply and validate the factory definition:
   * **Warp-managed factory:** Save the edits in the factory dashboard.
   * **GitHub-backed factory:** Merge the edits into the production branch.

   Confirm validation succeeds before testing. See [where the definition lives](/factories/factory-as-code/#where-the-definition-lives).

## Test the factory

1. Apply `factory-ready` to an issue that changes only one service. Check for one pull request with that service's check results and no merge-order requirements.
2. Apply `factory-ready` to an issue that adds an optional field to the provider's contract and displays it in the consumer. Check for two pull requests:
   * **Provider:** An additive contract diff and the provider's check results.
   * **Consumer:** A regenerated client and a passing contract check against the provider's branch. Record the check against the provider's current `main` too. If it fails because the consumer requires the new field, the description identifies that dependency as the reason the consumer merges second.
3. Apply `factory-ready` to an issue that renames a field in every response. Check that the foreman explains why the breaking change is out of scope and creates no branch.

## Troubleshooting

* **A service's bootstrap fails:** The image may lack its toolchain, or the command may run in the wrong directory. Use an image with every service's toolchain and start each setup command with `cd /workspace/REPOSITORY_NAME`.
* **The consumer's contract check fails against the provider's `main`:** This is expected when the consumer needs an unmerged contract change. Confirm the check passes against the provider's branch and record the `main` failure as the reason the consumer merges second. A failure against the provider's branch still needs a fix.
* **The agent tries to verify against a live service:** Runs start with repository checkouts, not deployed services. Point verification at contract files and fixtures, and document how to start test dependencies inside the sandbox.
* **The foreman accepts a breaking change as additive:** The compatibility instructions or contract-diff check may be incomplete. Explicitly prohibit removals, renames, type changes, and new required request fields, and require the provider's contract diff in verification.
