Plan how your organization will use Warp before rolling it out: who can access it, which inference configuration is allowed, where cloud work executes, and how you'll track usage. Start with those decisions, then configure the controls your developers need.

## Choose the workflow you're deploying

* **Interactive development** - Developers work with agents, commands, and code review in the [Warp app](/getting-started/quickstart/installation-and-setup/)
* **Standalone automation** - Run a bounded task from a schedule, integration, CLI, or API on the [{VARS.WARP_AUTOMATION_PLATFORM}](/platform/)
* **Repeatable development workflows** - Build your own workflow on [Warp Factories](/factories/), choosing its instructions, tools, and human decision points

These paths share some infrastructure but not every setup or compatibility rule. Use the reference for the path you choose rather than assuming a local credential or setting applies to cloud work.

## Configure access and administration

Start with [Getting started for enterprise](/enterprise/getting-started/getting-started-enterprise/) to plan onboarding. Configure [SSO](/enterprise/security-and-compliance/sso/) for your identity provider, then use the [Admin Panel](/enterprise/team-management/admin-panel/) to manage settings and access.

Check [roles and permissions](/enterprise/team-management/roles-and-permissions/) and [workspaces](/enterprise/team-management/workspaces/) before assigning administration. Repository access, agent tool permissions, and organization membership are separate controls.

## Choose inference and deployment

For centrally managed provider credentials, review [team-managed API keys and endpoints](/enterprise/enterprise-features/team-managed-keys-and-endpoints/). For inference through your cloud provider, review [Bring Your Own LLM](/enterprise/enterprise-features/bring-your-own-llm/). Confirm the provider, model, local-versus-cloud support, and plan requirements for the configuration you select.

Use [Architecture and deployment](/enterprise/enterprise-features/architecture-and-deployment/) to decide whether Warp-hosted execution or a supported self-hosted setup fits your network and data requirements. For factory execution and credential boundaries, see [Infrastructure and security](/factories/infrastructure-and-security/).

Ask your security team to review the current [Warp Security information](https://www.warp.dev/legal/security) and [Trust Center](/enterprise/security-and-compliance/trust-center/). Evaluate the exact data and contractual scope for your deployment rather than inferring it from a feature name.

## Share instructions and enforce checks

Use [Rules](/agents/capabilities/rules/), [skills](/agents/capabilities/skills/), and [Warp Drive](/knowledge-and-collaboration/warp-drive/) to share project conventions and runbooks. Rules instruct the agent; they don't enforce coding standards or security policy.

Configure [Agent Profiles and permissions](/agents/capabilities/agent-profiles-permissions/) for tool access, and keep required formatters, tests, approvals, and merge restrictions in your repository and CI. Trial a small change and inspect its diff and verification before expanding the rollout.

## Measure usage and results

Use team usage reporting and the [Analytics API](/enterprise/enterprise-features/analytics-api/) to inspect adoption and usage. For factories, compare output quality and cost on representative work before changing a model or workflow; see [Measure and improve a factory](/factories/measure-and-improve/).

Enterprise contract and billing questions belong with your account team. See [Enterprise billing](/enterprise/support-and-resources/billing/) or <a href={VARS.CONTACT_SALES_URL}>contact sales</a> for requirements specific to your organization.
