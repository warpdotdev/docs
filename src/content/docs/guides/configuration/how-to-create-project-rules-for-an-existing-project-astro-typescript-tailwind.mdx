Give the agent the project commands and conventions it needs for your next change, without copying your application's architecture into every request. Create or edit a short `AGENTS.md`, then test one instruction on a bounded task.

<VideoEmbed url="https://youtu.be/SCYovBn4TnM?si=7wZEuTQAFUpcoFJx" title="Creating project rules for an Astro TypeScript Tailwind project" />

The video uses an Astro application as its example. The steps below work with an existing repository; its own files determine which commands and conventions belong in your Rules.

## Prerequisites

* An existing Git repository open in Warp. If you're new to Agent Mode, start with [Coding in Warp](/getting-started/quickstart/coding-in-warp/).
* Access to the repository's setup instructions, package scripts, and required checks.

## 1. Open or create the project rules

In the Warp app, navigate to your repository. If it already has project Rules, enter `/open-project-rules` in the agent input to open the file.

For a repository without project Rules, enter `/init` and choose the option to generate `AGENTS.md`. Review the generated content before keeping it. If the setup offers to link an existing instruction file, inspect that file rather than creating a competing copy.

Warp uses `AGENTS.md` for new project Rules. Existing `WARP.md` files remain supported and take precedence when both files exist in the same directory. Use uppercase filenames. See [Rules for agents](/agents/capabilities/rules/#project-rules) for discovery and precedence.

## 2. Keep commands you can verify

Compare every generated command with the repository's README, package scripts, and CI configuration. Remove guesses and details the agent can look up when needed.

For example, this docs repository defines `npm run build` in `package.json` and keeps its public content under `src/content/docs/`. A short starting file for that repository could contain:

```markdown title="AGENTS.md example for warpdotdev/docs"
# Project instructions

Public documentation lives in src/content/docs/ as MDX.
Read the existing page and its related pages before editing.
Keep published page paths unchanged unless a move is approved.

## Validation

Run npm run build after changing MDX.
Report the command and its result. If a check cannot run, say why.
```

Use commands verified in your own repository, not this example's build command. Keep full architecture explanations in their owning documentation and link them when the agent needs them.

## 3. Add one convention and try a change

Edit the Rules file to add an instruction you can observe. For the docs example, add:

```markdown
Use sentence case for headings.
```

Then start a fresh conversation in that repository and send:

```text
Add a "Local development" section to README.md using the setup instructions
in CONTRIBUTING.md. Change only README.md. Follow the project Rules, run
the documented check, and report the exact command and result. Do not commit
or push; leave the diff for me to review.
```

Use this request only in a repository with `CONTRIBUTING.md`; otherwise name its actual setup document. Inspect the heading, compare the instructions with that source, and check the reported command in the conversation. Correct the rule if it was ambiguous, then retry a fresh small task.

Rules guide the agent; they don't enforce formatting or guarantee a passing build. Keep formatter, linter, test, and approval requirements in your repository's checks and access controls.

## 4. Scope specialized instructions

Keep shared instructions in the root file. Add a subdirectory's `AGENTS.md` only for guidance specific to that area.

Warp includes applicable project Rules based on your working directory. Rules for files edited elsewhere are included on a best-effort basis, so inspect which instructions the agent used rather than assuming every file is loaded. See [project Rules discovery](/agents/capabilities/rules/#project-rules).

## Troubleshooting

**The agent follows an older instruction.** Check whether a `WARP.md` shadows `AGENTS.md` in the same directory and inspect any applicable subdirectory Rules. Edit the file the agent actually uses.

**A generated command fails.** Verify the command and prerequisites against the repository's scripts and CI. Correct the Rules file rather than asking the agent to keep retrying a nonexistent command.
