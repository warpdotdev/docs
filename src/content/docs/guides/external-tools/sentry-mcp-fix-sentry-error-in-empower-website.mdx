Use Sentry error data to connect a stack trace to a local reproduction, then ask the agent for a patch you can test. The Empower Plant demo shows the workflow; reading an issue or generating a diff isn't evidence that the error is fixed.

<VideoEmbed url="https://youtu.be/rrxfS9u1XRA?si=fVUfjQJSOlyLFBJT" title="Investigating and patching an Empower error with Sentry MCP" />

In the recording, the agent investigates an error involving `.toUpperCase()` and an array. Your checkout and Sentry issue may differ; establish the cause from their actual source and event data.

## Prerequisites

* Warp with [MCP server support](/agents/capabilities/mcp/).
* A Sentry account authorized to read the issue and project you will investigate.
* A local checkout of [Sentry's Empower Plant demo](https://github.com/sentry-demos/empower/tree/master), or your own application with a reproducible error. Use a separate branch for the patch.

## 1. Connect Sentry for investigation

Add Sentry's remote MCP endpoint, `https://mcp.sentry.dev/mcp`, using [Warp's MCP setup](/agents/capabilities/mcp/#adding-an-mcp-server). Complete Sentry's OAuth flow with the account that can read your test project.

[Sentry's MCP documentation](https://docs.sentry.io/product/sentry-mcp/) also describes organization- and project-scoped URLs. Choose the narrowest project access that serves the investigation.

The server exposes more than issue inspection. Review requested tool calls and keep this investigation read-only in Sentry. Access to production event data is not permission to change production systems.

## 2. Reproduce one error locally

Follow the demo repository's [local setup instructions](https://github.com/sentry-demos/empower/tree/master#local-setup--development) for its toolchain and `local.env`. Point error reporting at a test project you control. The repository uses a setup script rather than root-level `npm install` and `npm start`.

From the repository root, its documented local React and Flask command is:

```bash
./deploy react flask --env=local
```

Despite its name, `--env=local` selects local servers. Review the script and configuration before running it; setup can still contact external services, and frontends can use remote backends that you haven't started locally.

Open the local address printed by setup. To try the checkout flow documented by Empower, add an item to the cart and attempt a purchase. Record the steps, selected backend, source commit, and observed error. In Sentry, find the matching test event and copy its issue URL. Don't assume an older event describes your current checkout.

## 3. Ask for a diagnosis before a patch

Attach the issue URL and reproduction to your prompt:

```text
Inspect the attached Sentry issue and my local checkout. Use Sentry only
to read issue data; don't change issue state, deploy, or modify production.
Compare the stack trace and release with this source commit.

Reproduce the reported failure locally using the attached steps.
Explain the cause and propose the smallest patch and a regression check.
Stop for my review before editing. If the event and checkout don't match,
or reproduction fails, report the gap instead of assuming a cause.
```

Review the source location, inputs, and proposed behavior. A type conversion that removes an exception may still return the wrong value. Resolve the intended behavior before authorizing edits.

## 4. Verify the patch

After approving the approach, ask the agent to implement it on the patch branch and add a regression test for the failing input. Require the same test to fail on the original code and pass on the patch.

Run the checks documented for the subproject you changed. Repeat the original local reproduction and check the expected application result, not only the absence of an exception. Inspect the diff for unrelated changes and include the actual check commands and results in the PR.

Keep deployment and any Sentry issue-state changes as separate human decisions. A local fix doesn't resolve the production incident until your normal release and monitoring process confirms it.

## Troubleshooting

**Sentry can't find the issue.** Check the connected account, project scope, and issue URL. Don't broaden access before confirming which project owns the event.

**The local app behaves differently.** Compare the Sentry release, backend selection, configuration, and source commit. Use the [Empower troubleshooting instructions](https://github.com/sentry-demos/empower/blob/master/troubleshooting.md) for setup failures.

**The exception disappears but checkout still fails.** Verify the returned data and expected application behavior. Extend the regression check rather than treating a quiet error stream as success.
