Turn a triaged GitHub issue into a pull request for human review, with GitHub Actions and labels controlling the handoffs. Extend the [triage](/guides/agent-workflows/build-a-triage-agent) and [spec](/guides/agent-workflows/write-product-and-tech-specs-with-agents) setup with implementation and review.

You own the orchestration in this path: workflow files select events, labels request the next step, and your team handles failures and approvals. For a standing workflow configured on Warp Factories infrastructure instead, start with the [Warp Factories quickstart](/factories/quickstart/). These examples don't configure a factory in the factory dashboard.

## Prerequisites

* A working [triage agent](/guides/agent-workflows/build-a-triage-agent) and [spec agent](/guides/agent-workflows/write-product-and-tech-specs-with-agents), each deployed individually
* A cloud environment with access to your repository ([create one](/factories/environments/))
* `warpdotdev/oz-agent-action` installed (see [GitHub Actions integration](/platform/integrations/github-actions))

## How the loop works

GitHub labels serve as the state machine that connects the agents. Each agent watches for a specific label, does its work, and applies the next label:

| Label | Agent triggered | What it does | Next label |
|-------|-----------------|--------------|-----------------|
| *(new issue filed)* | Triage agent | Reviews the issue, flags questions | `ready-to-spec` or `needs-info` |
| `ready-to-spec` | Spec agent | Writes `PRODUCT.md` and `TECH.md` | human sets `ready-to-implement` after review |
| `ready-to-implement` | Implementation agent | Opens a PR with code and specs | PR opening triggers reviewer |
| *(PR opened)* | Reviewer agent | Reviews PR against specs and conventions | Posts inline review comments |

A person approves the specs before requesting implementation and decides whether to merge after review. The other handoffs depend on enabled workflows, available usage, repository access, and the referenced skills. Check failed or blocked runs before retrying; a label is a request to start work, not proof that the preceding stage succeeded.

## 1. Trigger the spec agent when an issue is labeled ready-to-spec

Add a GitHub Actions workflow that runs when the `ready-to-spec` label is applied:

```yaml
name: Write specs for ready issues

on:
  issues:
    types: [labeled]

permissions:
  contents: write
  pull-requests: write
  issues: write

jobs:
  write-specs:
    if: github.event.label.name == 'ready-to-spec'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: warpdotdev/oz-agent-action@v1
        with:
          skill: spec-driven-implementation
          prompt: |
            Write a product spec and tech spec for GitHub issue #${{ github.event.issue.number }} in ${{ github.repository }}.
            Issue title: ${{ github.event.issue.title }}
            Issue body: ${{ github.event.issue.body }}
          environment: YOUR_OZ_ENVIRONMENT_SLUG
          warp_api_key: ${{ secrets.WARP_API_KEY }}
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The `spec-driven-implementation` skill from [`warpdotdev/common-skills`](https://github.com/warpdotdev/common-skills) automates what you did manually in the [previous guide](/guides/agent-workflows/write-product-and-tech-specs-with-agents) — running both spec commands in sequence and opening a draft PR so you can review and approve the specs before implementation begins.

## 2. Human review: approve the specs

When the spec agent opens a draft PR, review the `PRODUCT.md` and `TECH.md` files.

When the specs look right, make the approved files available on the branch the implementation run checks out, then apply the `ready-to-implement` label to the original issue. Confirm the implementation reads those approved files; the workflow below names a path but doesn't fetch a separate spec PR branch.

## 3. Trigger the implementation agent

Add a workflow that triggers when `ready-to-implement` is applied:

```yaml
name: Implement from approved specs

on:
  issues:
    types: [labeled]

permissions:
  contents: write
  pull-requests: write

jobs:
  implement:
    if: github.event.label.name == 'ready-to-implement'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: warpdotdev/oz-agent-action@v1
        with:
          skill: implement-specs
          prompt: |
            Implement the approved specs for GitHub issue #${{ github.event.issue.number }} in ${{ github.repository }}.
            The specs are in specs/${{ github.event.issue.number }}/.
          environment: YOUR_OZ_ENVIRONMENT_SLUG
          warp_api_key: ${{ secrets.WARP_API_KEY }}
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The `implement-specs` skill from [`warpdotdev/common-skills`](https://github.com/warpdotdev/common-skills) reads the product and tech specs, and builds against them. It opens a PR with the code changes and the spec files committed together.

## 4. Trigger the reviewer agent when a PR is opened

Add a workflow that triggers when a PR is opened or updated:

```yaml
name: Review new pull requests

on:
  pull_request:
    types: [opened, synchronize]

permissions:
  pull-requests: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: warpdotdev/oz-agent-action@v1
        with:
          skill: review-pr
          prompt: |
            Review pull request #${{ github.event.pull_request.number }} in ${{ github.repository }}.
            If spec files are included in this PR, locate the changed specs/*/PRODUCT.md and specs/*/TECH.md files and validate the implementation against them.
          environment: YOUR_OZ_ENVIRONMENT_SLUG
          warp_api_key: ${{ secrets.WARP_API_KEY }}
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The `review-pr` skill from [`warpdotdev/common-skills`](https://github.com/warpdotdev/common-skills) reviews the PR diff against your codebase conventions and, when spec files are available, validates the implementation against the specs. It posts inline review comments.

## 5. Human review: merge the PR

After the reviewer agent posts its comments, a human reviews the PR, including the diff, the agent's inline comments, and the spec files. Address any gaps, run the project's tests, and merge.

The reviewer agent surfaces issues and inconsistencies; the human makes the final call on quality and correctness. See [Review AI-generated code](/guides/agent-workflows/how-to-review-ai-generated-code) for the full human review workflow.

## Test the handoffs

Use a small test issue before enabling this path for your backlog. Confirm triage returns the intended label, spec drafting stops for your approval, implementation reads the approved specs, and review returns findings on the correct PR. Run the repository's checks before merging.

GitHub Actions events created using `GITHUB_TOKEN` generally don't start another workflow. This affects labels added by an action and PRs opened by an action. Check the [GitHub rules for triggering workflows](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow) and configure an appropriate GitHub App or token if a handoff needs to create a new workflow run.

## Troubleshooting

**A label or PR doesn't start the next stage.** Check the Actions event, workflow condition, token type, and secret availability. Verify that no run is already handling the issue before triggering another.

**Implementation can't find the specs.** Check the run's checkout branch and `specs/ISSUE_NUMBER/` path against the approved spec commit. Stop rather than asking the agent to infer missing requirements.

## Productivity tips

* **Validate before the reviewer runs** — After the implementation agent opens a PR, run `/validate-changes-match-specs` to check the diff against `PRODUCT.md` and `TECH.md`. This catches any misalignments before the reviewer agent posts comments. The skill is available from [`warpdotdev/common-skills`](https://github.com/warpdotdev/common-skills).
* **Start with triage only** - Test classification and readiness criteria before adding spec and implementation
* **Monitor runs in the {VARS.WEB_APP}** — Every cloud agent run appears in the <a href={VARS.WEB_APP_URL}>{VARS.WEB_APP}</a> with a session link. Use it to inspect what each agent did, steer a stuck run, or hand work back to a local session.
