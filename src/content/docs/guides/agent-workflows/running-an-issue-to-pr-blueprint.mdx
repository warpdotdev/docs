## Prerequisites

* Complete the [Warp Factories quickstart](https://docs.warp.dev/factories/quickstart/) for account, team role, and GitHub setup. Factory runs need available usage in your team's balance; add usage if needed. See [access and billing requirements](https://docs.warp.dev/platform/team-access-billing-and-identity/).
* Use two repositories you control: a disposable fork for the README change, and a separate repository for the factory definition. The first is the code agents work on; the second stores their workflow.
* Grant the Warp GitHub App access to both repositories. Runs need permission to read issues, update labels and comments, push branches, and open PRs. Keep human approval and merge requirements in your repository rules. See [GitHub permissions](https://docs.warp.dev/factories/integrations/github/#permissions).
* Install Git and Python 3 on the machine where you prepare and validate the definition. Validation requires network access to Warp's service.

   git push -u origin blueprint-demo

   Replace `YOUR_GITHUB_USER` with the account that owns the fork.

## 4. Send a request that requires a plan

You choose the scope and require approval even though this is a small change.

1. In your fork, create an issue titled `Document single-example validation`.
2. Apply `factory:blueprint-demo` before mentioning the foreman. Then post a new comment with `@warp` followed by:

   ```text title="Issue request"
   In the root README, document how to validate only the SDLC example with
   python3 scripts/validate_factory_files.py examples/02-sdlc-issue-to-pr.
   Explain that exit code 2 means validation did not run and is not a pass.
   Keep the change to README.md. Propose a short plan and wait for my approval
   before editing. Run the repository's convention check and report the
   validator result honestly. Open a draft pull request. Do not merge.
   ```

The GitHub automation supplies the request to the foreman. The foreman selects planning because your request explicitly requires it; the spec worker returns a plan and opens its review gate.

## 5. Answer the plan-review gate

Open the run conversation linked by the foreman. Read the plan, then reply:

```text title="Plan approval"
Approved. Keep the README-only scope, run the convention check, and open a
draft pull request. Do not merge.
```

The spec worker reports your answer, and the foreman routes the approved plan to implementation. If you request plan changes instead, the route must return to planning and ask for another answer before implementation.

## 7. Make the human handoff decision

Review the final diff, check results, and findings yourself. A successful agent review is advisory. Leave the PR open for review, request another revision, or merge it through your normal process when you choose.

This exercise stops before merge. The workflow must not treat delivery of a draft PR as a merge. If someone closes the PR without merging, the foreman must report closure rather than mark the work merged or complete.

## Troubleshooting

* **Validation cannot run** - Check Python, network access, and the service URL reported by the validator. Retry after restoring access; do not treat exit code 2 as success.
* **The mention produces no workflow run** - Confirm the app can access the fork and the applied automation's repository, handle, and label filters match. Apply the label, then send a new mention. This example's specialized automation does not handle nonmatching events; do not assume another route does.
* **An integration is unavailable** - Remove its declaration and automations together, or finish its connection before applying the definition.
* **Work is waiting for you** - Answer the question in the original conversation. A question back or an unrelated message does not approve a plan.
* **A definition change does not affect the current run** - Apply the definition and start separate test work. Follow-ups to the existing run keep its selected Blueprint.
