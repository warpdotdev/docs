Work on a UI fix while separate agents summarize a review queue and inspect logs. Give each task its own scope and evidence requirements; parallel execution doesn't make their answers complete or correct.

<VideoEmbed url="https://youtu.be/3jwus1bfKv4" title="Running a UI change, PR analysis, and log summary in parallel" />

The recording shows three independent agent tabs, not threads sharing one task. It reports 26 open PRs and a summary of 1,000 log entries after requesting 2,000. Those are observations from that demo, not expected results for your account. The log-count mismatch is a reason to check coverage before accepting the summary.

## Prerequisites

* A repository and a UI change with agreed acceptance criteria.
* A [separate Git worktree and branch](/code/git-worktrees/) for any agent editing code. Keep the other two tasks read-only.
* GitHub CLI access to the repositories being analyzed and `gcloud` access to the selected project's logs. Use existing read permissions; don't grant write access for reporting.

For setup and ownership patterns, follow [Run multiple AI coding agents](/guides/agent-workflows/how-to-run-multiple-ai-coding-agents/).

## 1. Give each tab one task

Open three agent tabs. Run the UI task from its assigned worktree. In each prompt, supply the actual issue, screenshot, repository, or account context the agent needs.

<Tabs>
  <TabItem label="UI change">

    ```text
    In this worktree, plan a change to the input pane shown in the attached
    screenshot and issue. Remove the border and background only when the pane
    is unfocused. Preserve the focused state and input behavior.
    Stop for approval of the plan before editing. After approval, run the
    repository checks and verify both focus states and keyboard input.
    Return the diff, check results, and visual evidence. Do not merge.
    ```

    Include the acceptance criteria and confirm the branch before approving edits.

  </TabItem>
  <TabItem label="Review queue">

    ```text
    Use the GitHub CLI to summarize open PRs awaiting review from the GitHub
    user I specify, in only the repositories I specify. Confirm whether I
    mean requested reviewer or assignee before querying.
    Keep this read-only. Report the exact filters, retrieval time, result
    count, and any pagination or access limits. For each PR, include its URL,
    author, age, draft status, and unresolved review threads.
    ```

    A PR assignee and a requested reviewer are different relationships. Check the filters and spot-check PR links before using the report to assign work.

  </TabItem>
  <TabItem label="Log summary">

    ```text
    Use gcloud to list projects I can access, then wait for my project choice.
    List that project's Cloud Run services and wait for my service choice.
    Ask me for a time window. Read logs only; don't change any cloud resources.
    Retrieve up to 2,000 entries and report the project, service, time window,
    exact filter, actual count, and any retrieval limits before summarizing
    severity counts and recurring errors. Distinguish the retrieved sample
    from all logs. Omit secrets and personal data from the summary.
    ```

    Don't treat a partial sample as the full incident history. Confirm whether fewer entries reflect the selected window, access restrictions, or a query limit.

  </TabItem>
</Tabs>

## 2. Monitor requests for input

Use the [Agent Management Panel](/platform/managing-cloud-agents/) in the Warp app to find active conversations and those needing attention. Open the relevant tab to review the UI plan or choose the log project, service, and time window.

If an analysis task needs a code change, stop and give that work a separate branch and scope. Don't let a read-only report expand into edits in the UI agent's worktree.

## 3. Check each handoff

| Task | Evidence to inspect | If evidence is missing |
| --- | --- | --- |
| UI change | Diff, repository checks, focused and unfocused states, keyboard behavior | Request the missing state or check before accepting the patch |
| Review queue | Repository list, reviewer-versus-assignee filter, pagination, PR links, unresolved threads | Rerun the query with corrected filters or report the access gap |
| Log summary | Source, time window, filter, actual count, severity totals, representative errors | Narrow the conclusion to the retrieved sample or retrieve the missing range |

Only the UI task produces a patch here. Review it before committing, and rerun checks after integrating it with other work. Neither a screenshot nor a claim that the fix is "accurate" proves the input still works.

## Troubleshooting

**Agents edit the same checkout.** Stop overlapping edits and move each code-writing task to its own worktree before continuing.

**A report returns fewer records than requested.** Inspect the actual query, pagination, time bounds, and permissions. Keep the shortfall in the report rather than silently summarizing a smaller dataset.

**The unfocused pane looks right but input breaks.** Test focus transitions and keyboard interaction alongside the visual change, then add a regression check for the missing behavior.
